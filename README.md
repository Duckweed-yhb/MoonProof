> **"我们文档里的例子还都对吗？"**

## 一句话

MoonBit 工具链迭代快，文档里的示例会不断腐坏——学习者照着敲得到编译错误然后卡住，而写文档的人并不知道哪些例子已经失效。**MoonProof 让示例像代码一样被 CI 持续验证。**

---

## 快速开始

```bash
moon run cmd/moonproof -- .
```

上面的命令会扫描当前目录下的 `.md` 文档，把每个 ```moonbit 代码块抽出来、在隔离工作区里真实编译（`run` 标注则真正运行），并输出每块的结果与失败归因。下面这个代码块由 MoonProof 在 CI 里**自举验证**（dogfooding）：

```moonbit
fn greet(name : String) -> String {
  "hello, " + name
}
```

## 目标用户与使用场景

### 用户
1. **官方文档 / 教程维护者**
2. **库作者**（README 与文档注释）
3. **高校课程与训练营讲师**
4. **MoonBit 工具链维护者**（发版回归）

### 三个完整使用场景（章程必填项）

**场景一 · 文档仓库 CI 门禁**
在文档仓库的 CI 里加一步 `moonproof run docs/`，任何过期示例直接让流水线红灯。防止"文档悄悄腐烂"。

**场景二 · 库作者自检 README**
库作者为自己的 README 与文档注释开启验证，保证"照着 README 敲一遍"永远能跑通——这是新库被采用的第一道门槛。

**场景三 · 课程材料批量校验**
高校宣讲、线上工作坊的配套讲义在每次开课前跑一遍，避免学员照着过期示例卡住。

**场景四（拓展） · 工具链发版回归**
工具链升级后跑一遍生态文档，得到"哪些生态文档被这次发版打破"的清单。

## 核心功能范围

### V1 必做（验收范围）

| 编号 | 功能 |
|:---:|---|
| F1 | 从 Markdown 文件抽取 ```` ```moonbit ```` 代码块（含信息串标注解析） |
| F2 | 从 `.mbt` 源文件的文档注释（`///`）抽取代码块 |
| F3 | 为每个代码块合成独立的最小包，写入一次性隔离工作区 |
| F4 | 调用真实工具链执行 `moon check`（默认）或 `moon test`（标注为可运行时） |
| F5 | **失败归因**：区分为「语法/类型错误」「API 已变更」「依赖缺失」「工具链不兼容」等类别 |
| F6 | **行号回填**：把合成包中的编译器行号映射回原文档的行号与列号 |
| F7 | CLI 输出（人读，含颜色与进度）+ `--json` 输出（CI 消费），失败即非零退出 |
| F8 | 库 API 可供其他工具 import 复用（非仅一个命令行程序） |
| F9 | `--list` 列出所有代码块及其标注状态（不执行），便于排查 |

### V1 明确不做（写进申报书，是加分项）

| 不做 | 原因 |
|---|---|
| **不做网站 / 不做文档渲染** | 会被判为"落地产品"，且不替代 `moon doc` |
| **不自动修复失效示例** | 只报告与定位，修改权交给文档作者 |
| **不做多工具链矩阵** | V1 只针对当前工具链；多版本对比留作后续方向 |
| **不执行未标注的任意副作用代码** | 默认只编译；仅标注为可运行的示例才在隔离区执行，带超时与配额 |
| **不做 Markdown 之外的格式** | V1 只覆盖 `.md`；AsciiDoc / reStructuredText 不做 |

## 代码块标注约定（待定型，V1 需先固化）

文档里大量片段是**片段性的**——只展示语法、故意写错来演示报错、依赖上一段上下文。因此**默认行为决不能是"必须能编译"**。

拟定标注（写在代码块信息串里）：

| 标注 | 行为 |
|---|---|
| ` ```moonbit ` | **默认：编译验证**（期望通过） |
| ` ```moonbit run ` | 编译 + 运行验证 |
| ` ```moonbit no-check ` | 跳过，不参与验证 |
| ` ```moonbit should-fail ` | **期望编译失败**（用于演示报错） |

> ⚠️ 这是**设计取舍点**，需要能被现有 Markdown 习惯接受。V1 开工前必须先实测几种写法在主流渲染器下的表现。

## 技术架构（拟定）

```
cmd/moonproof              CLI 入口：参数解析与分发（仅 native）
  │
features/                  应用层
  ├── scan                扫描目录、筛选 .md / .mbt
  ├── run                 编排：抽取 → 合成 → 执行 → 归因 → 报告
  └── report              控制台 / JSON 输出
  │
extract/                   抽取层（纯计算，全后端可移植）
  ├── markdown             Markdown 代码块抽取 + 信息串解析
  └── doccomment          .mbt 文档注释抽取
  │
synth/                     合成层（纯计算）
  └── package             代码块 → 最小可编译包 + 行号映射表
  │
diagnose/                  归因层（纯计算，全后端可移植）
  └── classify            编译输出 → 失败类别（复用 MoonHive 思路，规则重写）
  │
exec/                      执行层（仅 native，含 C FFI）
  ├── workspace           一次性隔离工作区（生命周期 / 配额 / 归属校验 / 清理）
  └── toolchain           调起 moon check / moon test，捕获输出，超时控制
```

**分层纪律**：`extract/`、`synth/`、`diagnose/` 是纯计算，**不 import 任何 FFI 包**，因此可在 `wasm` / `wasm-gc` / `js` / `native` 四后端编译与测试。边界用各 `moon.pkg` 的 `supported_targets` 声明、由工具链在构建期强制（该做法已在 MoonHive 验证过）。

## 验收标准（**能否过的关键**）

### 差分基准（现成，不需要发明）

> 拿官方文档仓库里真实存在的 MoonBit 代码块当输入。**每一块都曾由人类作者写过、且当时可编译。** MoonProof 输出一张"当前工具链下仍可用 / 已失效"的清单。
>
> **这份清单本身就是可验收产物**，且对官方文档有直接价值。

### 自举（dogfooding）

MoonProof 自己仓库 README 里的示例，**由 MoonProof 自己验证**，并写进 CI。评委看到这个，可信度直接拉满。

### 量化目标

| 指标 | 目标 |
|---|---|
| 抽取正确率 | 对官方文档仓库，抽取的代码块数量与人工计数一致 |
| 行号映射 | 100% 映射回原文档行号（抽样人工核对） |
| 归因准确率 | 抽样 20 个失败样本，人工判定归因类别是否正确 |
| 单元测试 | 核心功能路径全覆盖；纯计算层 100% 离线可测 |
| CI | Linux / Windows 双平台矩阵（检查 + 构建 + 测试 + 自举验证） |

## 技术风险与前置验证（**开工前必须先验的**）

| 风险 | 说明 | 前置动作 |
|---|---|---|
| **`moon test` 无按名过滤 flag** | [`moonbitlang/moon#1302`](https://github.com/moonbitlang/moon/issues/1302) 仍开着 → **不能**"所有示例塞一个包再筛选" | 已验证：改为**每示例合成独立最小包**，用包级选择执行。此约束决定架构 |
| 合成包的开销 | 每个示例一个包 + 一次 `moon` 调用，官方文档可能有数百块 | 实测单次开销；必要时引入进程池 / 增量缓存 |
| 行号映射复杂度 | 编译器报的是合成包行号，用户要的是原文档行号 | 合成时同步生成映射表，先写测试再写实现 |
| 标注约定的可接受性 | 若约定太别扭，用户不会用 | 实测几种写法在主流 Markdown 渲染器下的表现 |
| 平台层自建成本 | `moonbitlang/core` 不含 fs 与进程 | **复用 MoonHive 的 `platform/` 层经验**（见下节），不重复踩坑 |
